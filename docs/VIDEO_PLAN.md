# 后续宣传视频方案与待办

状态：已制作 4K 文档演示与两版发布会风格片头，继续优化镜头节奏和正片编排。项目基于 [PC2005-cloud/dsh-pet](https://github.com/PC2005-cloud/dsh-pet)，沿用素材的发布署名方式见 [关系核对](UPSTREAM_RELATIONSHIP.md)。

## 已确认的方向

- 以 4K 作为母版和平台发布目标，暂不安排 1080p 转换；展示更多动画，不强制控制在 15 秒内。实际画质要区分输出画布与角色源素材。
- 说明文字和版面改为更适合蓝发角色的蓝色系，不限定色号；可用柔和蓝白底、深蓝正文、少量亮蓝强调，避免浅蓝字与浅底缺少对比。
- 视频画面（含片头、片尾、字幕及录制到的软件界面）不展示 GitHub 仓库链接、二维码或变相网址，统一写 **GitHub 开源项目 · pet-with-you**，便于搜索项目名称或请 AI 协助安装。软件界面中已有的链接需通过取景或遮挡避开；仓库文档保留正常链接及来源说明。
- 用户希望画面不再单列“角色与动画来源”。发布所需的原作署名仍按来源说明与上游约定安排；视频不放网址的需求不改变素材许可。
- 修正额度卡片与角色过度重叠；先核对气泡锚点、角色可见范围、裁剪和缩放，录制验收时确保头部与主要动作不被卡片挡住。
- 纯桌宠、自有 API 与 Codex 联动分别演示，不能只演示连接账户。
- 配置过程、余额、模型、任务标题等统一使用演示数据；不展示真实密钥，密钥框和保存列表使用假数据及掩码。

## 尺寸与输出建议

以下是制作建议，不是对各平台当前上传规格的保证；发布时还需在实际上传页面检查限制与安全区域。

| 用途 | 建议尺寸与比例 | 排版方式 |
| --- | --- | --- |
| 抖音、小红书、微信视频号主视频 | 2160 × 3840，9:16 | 上方短标题，中间宠物/功能画面，下方精简说明 |
| GitHub、电脑观看和横屏介绍 | 3840 × 2160，16:9 | 文字与演示区域左右排布 |
| 小红书封面/补充图文 | 可另做 1080 × 1440，3:4 | 单个亮点与角色，按实际封面裁切预览调整 |

竖屏要重新布局，不能把横屏缩小塞入竖屏，也不能把完整设置界面缩到文字看不清。配置演示应分步放大具体模块。关键文字和角色避开屏幕最右侧按钮列、顶部标题和底部文案区，并用各平台预览检查。

当前文档演示采用 H.264 MP4、3840×2160、固定 24fps 离线合成，与源动画帧率一致。后续真实操作教程可按需要用 30/60fps；提高帧率不自动补出原动画细节。

建议一套素材输出两个版本：短视频平台先展示吸引人的互动，再说明亮点；仓库完整版保留更完整的设置和联动流程。主视频可先按 45–75 秒设计，长教程另做，不强迫所有内容塞入一个片段。

## 需要覆盖的内容

1. 短片头：从首个有效镜头开始显示“GitHub 开源项目 · pet-with-you”，并可搭配“可下载安装的桌面小伙伴”，让观众尽早知道这是可获取的软件。不要等到片尾才揭示项目身份。
2. 纯桌宠：随机动作、吃东西/玩耍、手动点播、拖动、吸附、禁止跑动。
3. 个性化：尺寸滑条、字体、模块排序和窗口策略，使用局部放大镜头。
4. 自有 API：假配置的保存/载入、聊天、流式碎碎念、自动碎碎念；避免把真实等待过程剪成“保证瞬间返回”。
5. 密钥/代理额度：CRS 演示统计、查询卡片、关闭/停留设置；与账户用量明确区分。
6. Codex 联动：单任务、多任务、等待与完成、反馈开关、5 小时/周额度。
7. 结尾：重复“GitHub 开源项目 · pet-with-you”，可加“搜索项目名称了解安装方式”；不出现仓库网址。

## 片头项目标识与发布验收（2026-09-28 补充）

- 生成式角色开场也必须叠加上述项目标识。文字优先在后期以矢量或高分辨率方式排版，不依赖视频模型生成英文，以免项目名称拼写出错。
- 保持蓝色视觉：浅底配深蓝字，深底配蓝白字；复杂角色背景加轻薄底板。项目名用较大字号，开源属性作为副标题，避免装饰性小字。
- 4K 竖屏可从项目名 100–140 px、副标题 64–88 px 试排；横屏按版面调整。这是起始值，最终以手机缩小预览仍清楚为准，并避开平台按钮及裁切区。
- 标识在片头持续可读，至少留出约 2–3 秒阅读时间；镜头切换时不要闪掉。制作完成后逐段检查链接露出、拼写、字号和对比度。
- 安装演示与当次 Release 保持一致；alpha.5 开始提供公开 EXE，视频发布前核对实际下载链接与版本可用。

## 4K 画质与实现路径

旧版 720p 实时截图录制器已替换。新版先捕获隔离桌宠的真实卡片并以 3 倍比例栅格化，再以 4K 文字底板与原始透明 WebM 离线合成，固定 24fps。不是 4K/60fps 桌面实时录屏。

2026-09-27 检查结果：106 段角色动画全部是 640×360、24fps。这个尺寸还包含透明背景，角色自身有效像素更少。将文件或视频放大到 4K，不会自动变成原生 4K 角色。

当前电脑检测到 NVIDIA GeForce RTX 5070 Laptop GPU，适合考虑硬件编码；尚未做 4K 持续吞吐和编码兼容性测试，不保证所有场景都实时 4K60。普通桌宠进程目前关闭硬件加速以兼容透明窗口；制作高质量媒体应建立独立渲染/编码链路，不能仅为录制随意改变正常桌宠的窗口策略。

建议输出：

| 产物 | 目标 | 说明 |
| --- | --- | --- |
| 横屏母版 | 3840×2160 | 用于仓库/电脑展示和后续压缩 |
| 竖屏母版 | 2160×3840 | 为竖屏重新布局，不能横屏直接拉伸 |
| 平台发布版 | 3840×2160 或 2160×3840 | 按横竖屏发布 4K，上传后检查平台二次压缩效果 |
| 文档静态配图 | 按最终展示尺寸 2 倍左右输出 PNG | 文字/UI 以目标分辨率绘制，避免低分辨率截图二次放大 |

拟采用离线逐帧合成：按预定时间点取得动画帧、以目标分辨率绘制文字和界面，再编码。它不依赖显示器刷新率，也允许慢于实时计算，优先保证帧序列完整。真实鼠标操作教程可另用合适的屏幕录制工具捕获，两种素材在后期组合。

帧率按片段决定：发布会式角色展示可使用 24/30fps；UI、文字和镜头动画可做 60fps。24fps 原角色不会仅因 60fps 输出多出新动作细节，不默认使用可能造成头发/五官变形的插帧。更高分辨率/帧率并非越高越好，当前瓶颈首先是素材与取景。

近距离眼睛、脸部、头饰等镜头尤其需要高清立绘、重新生成并校验的素材或专门修复的特写图。功能演示可保持宠物在画面中适当大小，把高分辨率收益用于清晰的文字、设置界面和构图。无需把低分辨率角色放到铺满整个 4K 画面。

### 适合本项目的改编

实际参考更接近“微距特写 → 特性介绍 → 全身揭示”的产品发布片，而不以多分屏为核心。建议借鉴其镜头组织、留白和介绍方式，使用蓝发桌宠自己的特点与蓝色视觉。

候选片头节奏（待制作前确认）：首个角色特写即带项目标识，短句引出角色；切到小动作与全身；迅速进入日常陪伴、自有 API 或 Codex 联动演示。主短片可用约 5–8 秒开场，完整版可以更长。每条宣传片也可只突出一种用户场景。

| 制作方式 | 难度 | 适用范围 |
| --- | --- | --- |
| 现有动画 + 高清文字/图形 + 裁切推拉 | 中等 | 全身动作、功能展示可行；过大特写会暴露现有素材分辨率 |
| 单独制作高清角色特写，再做 2.5D 镜头 | 中等至偏高 | 最适合实现类似参考的开场，需要检查角色一致性 |
| 持续环绕的真实三维角色 | 高 | 当前没有三维模型，需要额外建模/绑定，不是实现这种风格的必备条件 |

本轮已开始文档功能演示制作；发布会式新片头另行制作，不复用参考视频、Apple 标识、原视频配乐或文案。画面突出 GitHub 项目名称，原作署名按来源说明安排。


## 二维还是三维

当前建议保留二维角色外观，以高清二维特写、分层景深、光影和推拉镜头制作片头，也就是常说的 2.5D。这样能与实际桌宠保持一致，优先把制作时间用于画质、动作丰富度和功能表达。4K 是输出尺寸，与角色采用二维或三维无必然关系。

只有确定需要连续环绕、真实转身、多个角度一致的布光时，再考虑制作完整三维模型。它需要角色设计校准、建模、材质、绑定、动作和渲染；不建议只为几秒片头就更换整套表现方式。生成式多视图也不能保证发饰、脸和服装在各镜头完全一致，需要人工验收。

后续即使制作三维，也可以把动画预渲染成透明二维视频供现有桌宠播放，无需立即重写成实时三维应用。当前已有横屏 4K 文档演示制作流程，并开始二维片头试样；未制作三维模型。

### 第二版：表情与轻动作

用户认可第一版画风，希望参考 `assets/memes/` 增加俏皮动作，并评估眨眼、转身与 Live2D 表现。第二版延续原配色与立绘，参考 `Ciallo.png` 的眨眼比耶和 `吃白饭的大肥鱼.png` 的开心吃饭神态生成两个姿势；不搬用表情包文字。

11 秒横屏试片依次为：面部眨眼（0–1.8 秒）、比耶招呼与小幅弹跳（1.8–3.6 秒）、开心端饭与轻摆（3.6–5.6 秒）、日常陪伴全身（5.6–8 秒）、项目名收尾（8–11 秒）。保持第一帧起显示项目身份，无网址、无音轨。文件位于本机 `media-output/launch-intro-v2/`，第一版继续保留供比较。

当前动作由闭眼关键帧切换、整张立绘的轻微位移/旋转/缩放完成；不是已绑定的 Live2D，也没有连续转身、头发独立物理或连续吃饭动作。后续若增加真正的 Live2D，需要分别准备眼睛、头部、发束、身体等图层并绑定。优先完善短眨眼与轻微呼吸，确认角色稳定后再考虑小幅转头；不为几秒开场投入全套转身建模。

发布节奏建议：11 秒试片用于评估镜头；用户认可优化节奏，但不要求压到 5–7 秒，以镜头效果与阅读时间决定。片头后尽早衔接真实桌宠功能，避免迟迟看不懂软件用途。竖屏需重新构图，将角色表情和项目名放在平台控件的安全范围内。以上是剪辑判断，尚无平台发布后的留存数据验证。

### 第三版：片头与正片衔接

将第二版片头的最后三秒项目名单独收尾去掉，保留约八秒的眨眼、比耶、吃饭与陪伴镜头，随后直接切入真实桌宠。项目标识位置与配色全程一致，避免片头结束一次、正片又重新开场一次。
